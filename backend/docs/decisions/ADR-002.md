# ADR-002: Why Microservices (and when not to)

## Context
The explicit goal of this project is to demonstrate distributed-systems skills, not just AI skills. A monolith could implement the same business logic faster, but would not exercise service boundaries, independent deployability, or failure isolation.

## Decision
Split by business capability into 7 services (Gateway, Auth, Workflow, AI, Integration, Notification, Audit) -- each with a single, clearly-stated responsibility and its own schema. Deliberately capped at 7; no service exists 'for architecture's sake' (spec section 54).

## Alternatives Considered
- Modular monolith: faster to build and would satisfy the actual business requirement, but would not demonstrate independent deployability, per-service scaling, or failure isolation, which is the point of this portfolio project.

## Consequences
Higher operational complexity (7 Dockerfiles, network calls instead of function calls, eventual consistency between services) in exchange for: independent scaling of workers, failure isolation (AI Service down does not mean Workflow Service is down), and a codebase that maps directly to how this is discussed in a systems-design interview.
