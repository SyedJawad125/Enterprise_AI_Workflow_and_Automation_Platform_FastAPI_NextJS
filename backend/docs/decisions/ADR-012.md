# ADR-012: End-to-End Testing Strategy

## Context
Per-service unit/API tests (34 of them, run against SQLite/mocked
dependencies) verify each service's internal logic in isolation, but cannot
catch a contract mismatch between services -- e.g. Workflow Service expecting
a field name in a worker's callback payload that the worker doesn't
actually send. Only a test that exercises the real running stack over HTTP
can catch that class of bug.

## Decision
Two E2E tests live in `tests/e2e/`, written against the real docker-compose
stack via plain HTTP (`httpx`), no service internals imported and nothing
mocked: a happy-path test (login -> create -> execute a high-value refund ->
approval required -> approve -> COMPLETED -> audit trail verified by
correlation_id) and a failure-path test (execute against a nonexistent
order -> FAILED, not silently lost, not stuck WAITING_FOR_APPROVAL). Both
are marked `@pytest.mark.e2e` and self-skip via a session fixture if the
Gateway isn't reachable at `localhost:8000`, so a plain `pytest` run (in CI
without Docker, or a contributor's local machine without the stack running)
never fails because of this directory -- it's an opt-in suite, run
explicitly with `docker compose up -d && pytest tests/e2e -v -m e2e`.

## Alternatives Considered
- Mocking every service in the "E2E" test: rejected outright -- this is
  just a unit test wearing an E2E label; it would not have caught the kind
  of contract-mismatch bug this suite exists to catch.
- Testcontainers-style ephemeral stack spun up by the test suite itself:
  the more "correct" CI-native approach, but a meaningfully larger
  investment (container orchestration from Python) for a portfolio
  project's test suite; noted as a natural next step once this runs in a
  real CI pipeline with Docker-in-Docker available.

## Consequences
These tests require Docker and cannot run in this authoring environment
(no Docker daemon available in the sandbox they were written in) -- they
were verified via `python -m py_compile` and by manual trace of the
expected API contract, not by an actual green run against a live stack.
Anyone picking up this project should run them once against
`docker compose up -d` before trusting them as a regression gate; per-
service unit tests are the ones with a currently-verified green run.
