# ADR-003: Why RabbitMQ (not Kafka), and its Retry/DLQ Design

## Context
The platform needs to route AI/integration/notification work off the
request path, retry failed steps, and eventually dead-letter
permanently-failing messages. An early audit found the DLQ story
incomplete: exhausted Celery retries were being swallowed by application
code with nothing landing in an inspectable dead-letter queue, and the
audit consumer dead-lettered immediately on any failure with no retry
cascade at all. This ADR now also documents the corrected design.

## Decision
Use RabbitMQ as the broker, with topic exchanges + routing keys for audit
fan-out, and as Celery's broker for task dispatch. Retry/DLQ is implemented
in two places, deliberately differently, because the two consumers are
different kinds of components:

**Audit Service's raw-AMQP consumer** (the one place in the platform with no
task framework underneath it) implements the classic cascade your spec
describes explicitly: `audit.queue` -> on failure -> `audit.retry.queue`
(per-message TTL chosen from a 5s/15s/30s schedule, incrementing a
`x-audit-retry-count` header each attempt) -> TTL expires -> dead-lettered
back into `events.exchange` -> re-delivered to `audit.queue` -> after
`MAX_RETRIES` attempts, published directly to `audit.queue.dlq` instead.
This is implemented in `services/audit-service/app/consumer.py` and its
retry/DLQ *decision* logic (not the AMQP wiring itself, which needs a live
broker) is unit-tested in `tests/test_consumer_retry_logic.py`.

**The three Celery-backed processing queues** (`ai.processing.queue`,
`integration.processing.queue`, `notification.queue`) use Celery's own
`self.retry(countdown=...)` for the retry itself (see ADR-005/ADR-006 for
why Celery, not raw AMQP, owns retry here) using the SAME 5s/15s/30s
schedule via `shared/messaging/retry_policy.py` for consistency. What
RabbitMQ contributes on top: each queue is declared with an
`x-dead-letter-exchange`, and `task_acks_on_failure_or_timeout=False` means
a task that's done retrying and still fails is NOT acked -- so it dead-
letters into a real `<queue>.dlq`, inspectable in the RabbitMQ management
UI, rather than the failure existing only as an application log line.

## Alternatives Considered
- Kafka: excellent for high-throughput event streaming and replay, but its
  consumer-group/offset model is a worse fit for "process this one task,
  ack it, retry it individually, dead-letter it after N failures" than
  RabbitMQ's per-message ack/nack and DLX support.
- Redis Streams / Redis pub-sub: lighter weight, but weaker delivery
  guarantees and no native DLQ concept.
- Hand-rolling the same TTL-cascade retry queues for the three Celery
  queues too (instead of letting Celery retry them): rejected as redundant
  -- Celery already IS a retry mechanism, and re-implementing one
  underneath it on the same queues would be exactly the kind of
  unnecessary complexity the spec explicitly warns against. The audit
  consumer is the one place that pattern earns its keep, because it's the
  one consumer with no task framework already doing that job.

## Consequences
RabbitMQ's management UI gives free visibility into queue depth and DLQs
for the demo; the trade-off is no built-in replay/event-sourcing capability
the way Kafka has -- acceptable here since Audit Service (backed by
Postgres), not the queue, is the system of record for history. Having two
different retry mechanisms (raw AMQP cascade vs. Celery-native) in one
platform is a legitimate thing to be asked to justify in an interview; the
honest answer is "each consumer uses the retry mechanism appropriate to
whether it already has a task framework underneath it," not "for
consistency" -- consistency for its own sake would have meant picking the
worse-fitting tool in one of the two places.
