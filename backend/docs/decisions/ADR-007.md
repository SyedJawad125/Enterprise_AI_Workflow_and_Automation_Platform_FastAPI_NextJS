# ADR-007: Database-per-service (implemented as schema-per-service)

## Context
Each service should own its data so no other service can silently depend on its internal table structure.

## Decision
One Postgres instance (for local-dev simplicity) with one schema per service (auth, workflow, ai, audit, integration); cross-service data needs go through the owning service's REST API, never a cross-schema JOIN.

## Alternatives Considered
- True database-per-service (separate Postgres instances/containers): the 'correct' production answer, giving physical as well as logical isolation, at the cost of 4-5x the local Postgres containers and connection overhead for a portfolio project.
- Fully shared schema: rejected outright -- this is precisely the coupling the spec forbids (section 4).

## Consequences
Logical isolation is enforced by discipline (no service's SQLAlchemy models reference another schema) rather than the database engine; documented explicitly as the gap between this build and true production isolation.

**Migration strategy update:** an audit found `Base.metadata.create_all()` (fine for a fresh database, but incapable of evolving an existing one) was the only schema-management mechanism anywhere, despite earlier documentation claiming otherwise for workflow-service. `workflow-service` now has a real Alembic setup (`services/workflow-service/alembic/`, async-engine-aware `env.py`, a hand-written initial migration since no live database was available to autogenerate against) and its Dockerfile runs `alembic upgrade head` before starting the app. The other three stateful services (auth, ai, audit) still use `create_all()` at startup and should be migrated to the same Alembic pattern before any of them needs a real schema change in a deployed environment -- tracked as a remaining limitation, not silently left undocumented.
