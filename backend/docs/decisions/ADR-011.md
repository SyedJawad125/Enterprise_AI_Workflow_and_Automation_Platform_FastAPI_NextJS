# ADR-011: Idempotency at the API Layer (Workflow Execution)

## Context
Idempotency was originally implemented only on `POST /payments/refund`
(Integration Service). An audit against the fuller spec found this
insufficient: `POST /api/v1/workflows/{id}/execute` itself needed the same
protection -- a frontend retry after a dropped connection, or a double
button-tap, must not create two separate workflow executions for the same
logical request.

## Decision
`WorkflowExecution` gained an `idempotency_key` column, unique per
`workflow_id` (not globally unique -- the same key can be reused safely for
a different workflow). The Gateway forwards an incoming `Idempotency-Key`
header through unmodified; Workflow Service checks for an existing execution
with that `(workflow_id, idempotency_key)` pair before creating a new one,
returning the existing execution (flagged `idempotent_replay: true`) instead
of starting a second one. This is the same pattern already used for
refunds, applied one layer up the call chain.

## Alternatives Considered
- Idempotency only at the refund layer (the original state): technically
  prevents double-refunding, but does nothing to prevent double-*executing*
  a workflow whose non-refund side effects (a support ticket created twice,
  two notification sends) aren't otherwise guarded.
- A separate `idempotency_keys` table with a TTL/cleanup job: more general,
  but overkill here -- reusing the execution row itself as the idempotency
  record is simpler and the data naturally lives forever anyway (it's the
  execution history).

## Consequences
Every side-effecting entry point in the platform (workflow execution,
refund) now has the same idempotency guarantee. The trade-off is one extra
indexed lookup on every execute call when a key is supplied; negligible at
this scale, and skipped entirely when no key is provided (idempotency is
opt-in per the header's presence, matching how most real APIs implement it).
