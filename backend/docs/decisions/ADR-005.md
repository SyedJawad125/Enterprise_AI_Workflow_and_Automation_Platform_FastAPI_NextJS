# ADR-005: Why Celery

## Context
AI calls, external API calls and notifications are exactly the kind of work that must survive a process restart, be retried with backoff, and scale independently of the request-serving processes.

## Decision
Use Celery (broker=RabbitMQ, backend=Redis) for all three worker types, with task_acks_late=True and per-task autoretry_for / retry_backoff / max_retries.

## Alternatives Considered
- FastAPI BackgroundTasks: runs in-process, dies with the process, cannot be scaled or retried independently -- fine for fire-and-forget logging, wrong for a refund call.
- Dramatiq / RQ: viable alternatives; Celery was chosen for maturity and first-class RabbitMQ support.

## Consequences
Workers can be scaled horizontally (docker compose up --scale ai-worker=3) independently of the API services; retry/backoff policy lives with the task definition, keeping it close to the code that needs it.
