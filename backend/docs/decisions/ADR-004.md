# ADR-004: Why Redis

## Context
Need fast, ephemeral storage for rate-limit counters and short-lived execution state / distributed locks, and a Celery result backend.

## Decision
Use Redis for: (1) Gateway rate limiting (fixed-window counters), (2) Celery result backend, (3) documented extension point for distributed locks if a future step needs one (e.g. preventing two workers from processing the same idempotency key concurrently).

## Alternatives Considered
- Postgres for the same purposes: possible, but adds write load and latency to a hot path (every request checks the rate limit) that Redis is purpose-built for.
- In-memory counters per Gateway instance: would break the moment the Gateway is scaled to more than one replica -- the whole reason for a distributed counter.

## Consequences
Redis is never the source of truth for business data (only Postgres is); losing Redis loses rate-limit state and task-result caching, not workflow correctness, since worker-to-Workflow-Service callbacks (not the Celery result backend) drive state transitions.
